# Blazor Interactivity Mode Decision — Per Page/Component vs Global

**TL;DR**: For the bake-off, choose **`Per page/component`** (the default in modern Blazor). This is the most realistic and gives you the best comparison to React, Vue, and Angular.

---

## Understanding the Two Options

### Option 1: **Global** (Static Server Rendering for Everything)

```bash
dotnet new blazor -o PartsBlazor --interactivity Global
```

**What it means:**
- **All pages and all components** are rendered on the server
- No interactivity islands; everything is server-rendered HTML
- Component state lives on the server
- User interactions require round-trips to the server

**Pros:**
- Simplest architecture (no hybrid complexity)
- Works in any browser (no JS needed)
- Best for mostly static pages
- Smallest initial bundle

**Cons:**
- 🔴 **Slower interactions** (latency on every button click, form input)
- 🔴 **Poor UX** (lag, spinner on every interaction)
- 🔴 **Not representative** of modern Blazor (Blazor is meant to be interactive)
- 🔴 **Bad comparison** to React/Vue/Angular (those are all client-side interactive)

**When to use:**
- Dashboard with mostly read-only data
- Internal LOB apps with low-latency networks
- Very simple CRUD without complex interactivity

---

### Option 2: **Per page/component** (Auto/Hybrid — Recommended ✅)

```bash
dotnet new blazor -o PartsBlazor --interactivity Auto
```

**What it means:**
- **Server renders the initial page** (fast TTL, no JS bloat)
- **Interactive components** run in WebAssembly (client-side, instant interactions)
- **Best of both worlds**: Server rendering speed + client-side responsiveness
- Components opt-in to interactivity with `@rendermode InteractiveServer` or `@rendermode InteractiveWebAssembly`

**Pros:**
- ✅ **Fast initial page load** (server rendering)
- ✅ **Instant interactions** (WebAssembly for modal, forms, grid)
- ✅ **Realistic** (modern web app architecture)
- ✅ **Fair comparison** to React/Vue (client-side interactivity where it matters)
- ✅ **Production-ready pattern** (what companies actually use)
- ✅ **Demonstrates Blazor's hybrid strength** (SSR + WASM)

**Cons:**
- Slightly more complex (hybrid model)
- Larger bundle than pure server rendering
- Must understand render modes (`InteractiveServer` vs `InteractiveWebAssembly`)

**When to use:**
- Interactive CRUD apps (like Parts Manager)
- Multi-page apps with forms and real-time feedback
- Modern web applications
- **THIS BAKE-OFF** ✅

---

## For Your Bake-Off: Choose Per page/component (Auto)

### Why?

1. **Represents modern Blazor correctly**
   - Blazor's big advantage is "C# end-to-end with strong typing + interactive client-side code"
   - Pure server rendering (Global) doesn't showcase this

2. **Fair comparison to other frameworks**
   - React, Vue, Angular all have client-side interactivity
   - If you use Global, your app will feel slow compared to theirs
   - Evaluators will think "Blazor is sluggish" when really you're just comparing server-rendering vs client-rendering

3. **The Parts Manager is interactive**
   - Modal dialogs, form validation, sorting/filtering
   - These need instant feedback; server round-trips would feel laggy
   - Global rendering would require a page refresh to see results

4. **Blazor's real strength is hybrid**
   - The Auto/Per-component mode is where Blazor shines
   - It's the reason PartsCheck should consider Blazor

5. **Realistic evaluation**
   - This is how you'd actually build this in production
   - Evaluators want to know: "Would we use this in real projects?"
   - Answer: Yes, if it feels responsive (which it will with Auto)

## The Three Render Modes Explained

When you choose **Per page/component**, you have three options for each component:

### 1. **@rendermode InteractiveServer**

```razor
@rendermode InteractiveServer

<button @onclick="HandleClick">Click Me</button>

@code {
    private void HandleClick() { /* runs on server */ }
}
```

**How it works:**
- Server-rendered initially (fast page load)
- WebSocket connection to server for interactivity
- C# `@onclick` handler runs on the server
- Result streamed back to client

**Pros:**
- No WASM download (smaller initial bundle)
- Access to server resources directly (databases, APIs)
- Real-time connection to server

**Cons:**
- Requires WebSocket (doesn't work in all environments)
- Slightly higher latency than client-side
- Requires server to maintain connections

**Use for:**
- Your data grid, forms, modals
- Most of the Parts Manager

---

### 2. **@rendermode InteractiveWebAssembly**

```razor
@rendermode InteractiveWebAssembly

<button @onclick="HandleClick">Click Me</button>

@code {
    private void HandleClick() { /* runs in browser */ }
}
```

**How it works:**
- Server renders the page shell
- WebAssembly bundle downloads (C# runtime + your code)
- Click handlers run **in the browser** (instant, no round-trip)
- Can call APIs directly

**Pros:**
- Instant interactions (no server round-trip)
- Works offline (after initial load)
- Pure client-side (no server connection needed)
- Smallest possible latency

**Cons:**
- Larger initial bundle (WASM ~2-5 MB gzipped)
- Slower initial page load
- Can't access server resources directly

**Use for:**
- Heavy client-side interactivity (modals, real-time features)
- If you want to highlight Blazor's client-side capability

---

### 3. **@rendermode Auto**

```razor
@rendermode Auto

<button @onclick="HandleClick">Click Me</button>

@code {
    private void HandleClick() { /* smart routing */ }
}
```

**How it works:**
- Server renders initially
- Browser detects if component needs interactivity
- If interactive: loads WebAssembly and runs client-side
- If static: stays server-rendered
- Best of both worlds

**Pros:**
- Optimal performance (static pages stay server-rendered, interactive components use WASM)
- Fastest page load + instant interactions
- Simplest to reason about (framework handles the complexity)

**Cons:**
- Slight complexity (you don't directly choose mode per component)

**Use for:**
- **Your bake-off** (recommended)
- Production apps where you want zero overhead

## Comparison Table: All Three Modes

| Aspect | Global (Server Only) | InteractiveServer | InteractiveWebAssembly | Auto (Recommended) |
|--------|----------------------|-------------------|------------------------|-------------------|
| **Initial Load** | Fast (HTML only) | Fast (HTML only) | Slow (WASM download) | Fast (HTML only) |
| **Interaction Speed** | Slow (server round-trip) | Fast (WebSocket) | Instant (client-side) | Instant (WASM) |
| **Bundle Size** | Tiny | Small | Large (+2-5 MB WASM) | Medium (WASM only for interactive) |
| **Network Required** | Always | Always (WebSocket) | After initial load | Always |
| **Offline Support** | ❌ | ❌ | ✅ (after load) | ❌ |
| **Good for Bake-off?** | ❌ Too slow | ✅ Good | ✅ Good | ✅✅ Best |
| **Represents Real Blazor?** | ❌ No | ✅ Yes | ✅ Yes | ✅✅ Yes |

## Recommendation for Your Bake-Off

### **Use: Per page/component with `@rendermode Auto`**

**Setup command:**
```bash
dotnet new blazor -o PartsBlazor --interactivity Auto
```

**Why:**
1. ✅ Blazor renders pages on server (fast initial load)
2. ✅ Interactive components (modal, grid, forms) use WebAssembly (instant interactions)
3. ✅ Fair comparison to React/Vue (they're client-side, this is too)
4. ✅ Realistic production architecture
5. ✅ Showcases Blazor's hybrid strength
6. ✅ Your app will feel snappy, not sluggish

### **In Your Code:**

Most of your components should use `@rendermode InteractiveServer`:

```razor
@* Components/UI/PartsGrid.razor *@
@rendermode InteractiveServer

<div class="grid-container">
    <table>
        @* grid displays instantly *@
    </table>
</div>
```

Static pages (like Home.razor) don't need a render mode (they default to static server rendering):

```razor
@* Components/Pages/Home.razor *@
@page "/"

<div class="welcome">
    <h1>Welcome</h1>
    @* No @rendermode needed; static HTML *@
</div>
```

## What Happens During the Bake-Off

When evaluators test your app:

1. **First click on Parts Manager** → Page loads from server in ~1-2 seconds
2. **Click "Add Part"** → Modal opens **instantly** (WebAssembly running)
3. **Type in form field** → Validation runs **instantly** (client-side)
4. **Click Save** → HTTP call to json-server, result renders **instantly**
5. **Sort table** → Table resorts **instantly** (client-side logic)

**vs. if you used Global:**

1. Click Parts Manager → Page loads in ~1-2 seconds
2. Click "Add Part" → Page waits for server (2-3s latency), modal opens
3. Type in form → Each keystroke waits for server validation
4. Click Save → Server round-trip (1-2s), page refreshes
5. Sort table → Server round-trip (1-2s), page refreshes

**Clear winner**: Auto/Per-component. Your app feels modern and responsive.
