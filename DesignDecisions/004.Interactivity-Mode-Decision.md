# Blazor Interactivity Mode Decision — Per Page/Component with InteractiveServer

**Status**: Accepted — implemented.

**TL;DR**: Interactivity is configured **per page/component**, and every interactive component uses **`@rendermode InteractiveServer`**. There is no WebAssembly project in the solution.

> **History**: an earlier revision of this document recommended `Auto` (hybrid Server + WebAssembly). That was not what got built, and the reasoning behind it did not survive contact with the app — see [Why not Auto/WebAssembly?](#why-not-autowebassembly) below. This revision records the decision as implemented.

---

## The Decision

**Interactivity location**: Per page/component (not Global).
**Render mode**: `InteractiveServer` for every interactive component.

```bash
dotnet new blazor -o PartsBlazor --interactivity Server
```

In `Program.cs`:

```csharp
builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents();
// ...
app.MapRazorComponents<App>()
    .AddInteractiveServerRenderMode();
```

Interactive components opt in explicitly:

```razor
@* Components/UI/PartsGrid.razor *@
@rendermode InteractiveServer
```

Applied to: `PartsGrid`, `PartsForm`, `ConfirmDialog`, `Header`, `Sidebar`, `ContactUs`. Static pages (`Home`, `Reports`, `Settings`, `NotFound`, `Error`) carry no render mode and stay statically server-rendered.

---

## Why per page/component rather than Global?

"Global" and "per page/component" describe *where interactivity is declared*, not whether the app is interactive:

- **Global** — every component in the app is interactive. Simple, but it makes genuinely static pages (Home, Reports, Settings) hold a circuit and pay the interactivity cost for nothing.
- **Per page/component** — components opt in with `@rendermode`. Static pages render as plain HTML and cost nothing.

Per-component wins here because the app is genuinely mixed: five static pages, six interactive components. It's also the default shape of a modern Blazor Web App, so it's the honest thing to show in a bake-off.

## Why InteractiveServer?

### 1. The API is server-side, and that's a feature

`Services/PartsService.cs` is a typed `HttpClient` running in the ASP.NET Core process. Components inject it and call it directly in C#. Consequences:

- json-server needs **no CORS configuration**.
- The API URL (`ApiUrl` in `appsettings.json`) is **never exposed to the browser** — it isn't reachable or discoverable from client-side JS.
- In a real deployment, the API can stay on a private network with no public load balancer at all.

Under WebAssembly this inverts: `PartsService` would run in the browser, so the API becomes internet-facing and needs CORS, its own public ingress, and edge authentication. That's a materially larger surface area for a bake-off demo.

### 2. "Instant interactions" is mostly an illusion for *this* app

The original argument for WASM was that client-side handlers avoid server round-trips. That argument is much weaker than it looks here, because **the grid's paging, sorting, and filtering are all server-side API operations**:

```csharp
var url = $"{ApiUrl}?_page={page}&_limit={limit}";
if (!string.IsNullOrEmpty(sortBy))    url += $"&_sort={sortBy}";
if (!string.IsNullOrEmpty(filter))    url += $"&q={filter}";
```

Sorting the table hits json-server. Changing page hits json-server. Filtering hits json-server. Under WASM those become browser→API HTTP requests instead of browser→server WebSocket frames — a *swap* of one network round-trip for another, not an elimination. The earlier revision of this document claimed "Sort table → Table resorts instantly (client-side logic)"; that was never true of the implementation.

### 3. No WASM download

`InteractiveServer` ships no .NET runtime to the browser. First paint is fast and stays fast, with no 2–5 MB download and no second-visit-is-faster asterisk to explain to evaluators.

### 4. Debugging is straightforward

C# breakpoints in component code just work in a normal server debug session — no browser debug proxy, no WASM symbol loading. For a bake-off where the team is evaluating developer experience, this matters.

## Why not Auto/WebAssembly?

`Auto` does **not** mean "the framework detects which components need interactivity." Its actual behaviour:

1. **First visit** — the component runs on the **server** (via SignalR) while the WASM runtime downloads in the background.
2. **Subsequent visits** — once the runtime is cached, the component runs in **WebAssembly**.

So Auto doesn't avoid the server circuit; it adds a second execution mode on top of it. That has real costs:

- **Every component must work in both modes.** No direct server resource access, no assuming server-only services. `PartsService` would have to be rewritten as a browser-safe HTTP client — which drags in CORS and a public API, per point 1 above.
- **Two runtimes to reason about** when something breaks.
- **A separate `.Client` project** to maintain, with its own DI registration and shared model assembly.

For an app whose every meaningful interaction is an API call anyway, that complexity buys very little. The one place WASM would genuinely win is the SKU autocomplete in `PartsForm` — `PartsService.SearchCatalog()` is an in-memory lookup, so under WASM it would filter without touching the network at all, whereas today each keystroke costs a WebSocket round-trip. That's a real but narrow advantage, and not worth restructuring the solution for.

## Comparison

| Aspect | Global | **InteractiveServer** ✅ | InteractiveWebAssembly | Auto |
|---|---|---|---|---|
| Initial load | Fast | **Fast (HTML only)** | Slow (WASM download) | Fast first visit |
| Interaction latency | Round-trip | **WebSocket round-trip** | Local, but API calls still hit network | Server, then local after cache |
| Bundle size | Tiny | **Small** | +2–5 MB WASM | +2–5 MB, deferred |
| API can stay private | ✅ | **✅** | ❌ needs public + CORS | ❌ needs public + CORS |
| Projects to maintain | 1 | **1** | 2 | 2 |
| Offline after load | ❌ | ❌ | ✅ | ✅ (once cached) |
| Static pages stay free | ❌ | **✅** | ✅ | ✅ |

## Consequences

Recording these honestly, because they're the real cost of this decision:

- **Every UI event is a network round-trip.** Keystrokes in the SKU autocomplete, modal open/close, and grid interactions all cross the wire. On a low-latency network this is imperceptible; over a poor connection it is not.
- **Server holds per-user state.** Each connected client occupies a circuit with its component state in server memory. Scaling is bounded by concurrent circuits, not request rate.
- **Deployment requires sticky sessions and WebSocket support.** The circuit is pinned to one instance — the SignalR `negotiate` call and every subsequent frame (or long-poll, on fallback) must reach the same server. Without session affinity you get intermittent disconnects that are painful to diagnose.
- **Connection loss is user-visible.** Hence `Components/Layout/ReconnectModal.razor`.
- **UI events don't appear in the browser's Network tab.** They're WebSocket frames on `/_blazor?id=...`, not HTTP requests — DevTools → **WS** filter → the `_blazor` row → **Messages**, with DevTools opened before page load.

## If we revisit

The migration path is not catastrophic but it isn't free. Switching to `InteractiveWebAssembly` or `Auto` means: adding a `.Client` project, moving components and models into it, rewriting `PartsService` registration for the browser, exposing json-server (or a real API) publicly with CORS, and adding auth at the edge. Worth doing if the bake-off criteria come to weight offline capability or per-keystroke latency heavily — not otherwise.
