# Blazor — Bake-off Objective Measurements

**Status**: Draft for review.

The six objective numbers from the Bake-Off Kit §5, measured against a real production
build. This is the companion to [005 — Subjective Measurements](005.Bakeoff-Subjective-Measurements.md);
where that document records judgement, this one records only what a command printed.

> **Scope caveat, stated up front**: these numbers are **Track A (`blazor.demo`) only**.
> Doc 005 evaluates two independent implementations, and Track B (`blazor.demo.mia`,
> MudBlazor, no authored TypeScript) will produce materially different figures on at
> least four of the six metrics — it has no npm install in its build, no TypeScript
> compile, a component library in its bundle, and 10 tests instead of 2. **Do not enter
> these numbers on the scoring sheet as "Blazor" without also measuring Track B.**

| Metric | Result |
|---|---|
| **Time to build** | **~9h44m** wall-clock across 4 sessions (lower bound) |
| **Lines of code** | **2,484** app source · 2,557 incl. both test suites |
| **Production bundle** | **91.1 KB gzip** static first-load · **101–108 KiB** actually transferred |
| **Cold load** | **FCP 1.7s · LCP 1.8s · TTI 1.9s**, Lighthouse **98** (mobile, Slow 4G + 4× CPU) |
| **Dependencies** | **0** runtime deps added · 3 npm dev · 6 test NuGet |
| **Build/CI time** | **~78–87s** clean install + Release build |

Measured at commit `f03aec6` ("Added TS unit tests").

## Methodology

| | |
|---|---|
| Host | Windows 11 Pro 26200 |
| SDK | .NET 10.0.302, `net10.0` target |
| Node | v24.19.0 |
| Counter | `cloc` 2.06 |
| Auditor | Lighthouse 12.8.2, headless Chrome |
| App under test | `dotnet publish -c Release`, run with `ASPNETCORE_ENVIRONMENT=Production` |
| API | `json-server@0.17.4` on `:4000`, as per the kit |

Everything was measured against the **published Release output**, not `dotnet run` and not
a Development-environment server. Build timings were taken after deleting every `bin`,
`obj` and `node_modules` under the solution.

**Read the build timings with suspicion.** This machine was under concurrent load during
measurement and the same clean build ranged from 78s to 164s. Repeat runs are reported
rather than a single figure. The Lighthouse runs were repeated for the same reason — a
single `/parts` run reported a Speed Index of 6.8s that did not reproduce across three
subsequent runs (1.7–2.4s). **Any single-shot number on this hardware is noise; the
comparison against the other four frameworks must use repeated runs.**

## 1. Time to build — ~9h44m

There is no time log, so this is derived from commit timestamps: for each working day,
the span from its first to its last commit.

| Session | Span | Hours | Commits |
|---|---|---|---|
| 7 Aug | 13:34 → 15:18 | 1.74 | 4 |
| 10 Aug | 10:30 → 15:57 | 5.46 | 8 |
| 14 Aug | 16:03 → 16:17 | 0.24 | 4 |
| 17 Aug | 09:52 → 12:10 | 2.29 | 5 |
| | **Total** | **9.73 h** | 21 |

**This is a lower bound, and the error is one-directional.** The method cannot see work
done before each session's first commit, and it counts a day's final commit as the end of
work. It also cannot distinguish thinking from typing, or separate the Parts Manager from
the four other pages Track A built alongside it (Home, Contact Us, Reports, Settings) —
so it overstates the cost of the common app while understating total effort.

Treat it as "roughly a day and a bit of focused work", not as a measured figure. If the
other four frameworks are self-reported from a timer, this number is not comparable to
them and should be re-derived the same way for all five.

## 2. Lines of code — 2,484

`cloc` over the app project, excluding `bin`/`obj`/`node_modules`, the vendored Bootstrap
in `wwwroot/lib`, the generated `.razor.js` / `.js.map` output, and `package-lock.json`.

| Language | Files | Code |
|---|---|---|
| Razor | 18 | 1,099 |
| CSS | 13 | 868 |
| TypeScript | 11 | 297 |
| C# | 3 | 123 |
| JSON (config) | 5 | 80 |
| MSBuild | 1 | 17 |
| **App source** | **51** | **2,484** |

Adding both test suites — `PartsServiceTests.cs` (xUnit) and `UserActivity.razor.test.ts`
(`node:test`) — brings it to **54 files / 2,557 lines**.

**The interesting split is not C# versus TypeScript, it is code versus CSS.** Hand-written
CSS is 868 lines, or **35% of the app** — more than every `.cs` and `.ts` file combined
(420). That is the cost of "bring your own" styling, and it is the single largest
line-count item after the Razor markup itself. Track B's MudBlazor figure is the direct
comparison and will show what a component library buys.

C# is strikingly small at 123 lines because the framework absorbs so much: routing,
DI, HTTP, and rendering are all configuration rather than code.

## 3. Production bundle — 91.1 KB gzipped

Blazor Server, so there is no WebAssembly runtime to download. The static first-load
payload, taken from the `.gz` / `.br` variants the build actually emits and serves:

| Asset | Raw | Gzip | Brotli |
|---|---|---|---|
| `_framework/blazor.web.js` | 195.9 K | 54.3 K | 46.5 K |
| `lib/.../bootstrap.min.css` | 227.4 K | 30.2 K | 22.2 K |
| `PartsBlazor.styles.css` | 22.3 K | 3.8 K | 3.3 K |
| `app.css` | 2.8 K | 1.5 K | 1.3 K |
| favicon | 1.1 K | 1.2 K | — |
| **Total** | **449.5 K** | **91.1 K** | **73.3 K** |

Lighthouse independently measured **101 KiB** transferred on `/`, **108 KiB** on `/parts`.
The difference between 91 KB and 101 KB is the JS interop modules, which the table above
excludes because they load per-component.

**The app's own code is a rounding error.** Of the 91 KB, roughly 84 KB is framework plus
Bootstrap. Everything written for this project — all the CSS isolation, all the interop —
is about 7 KB gzipped.

### Finding: 75% of the shipped interop JavaScript is source map

Commit `f03aec6` changed `tsconfig.json` from `"sourceMap": true` to
`"inlineSourceMap": true` + `"inlineSources": true`. That embeds both the map *and the
original TypeScript source* as a base64 blob inside every `.js` file that ships.

| | Raw | Gzipped |
|---|---|---|
| Shipped `.razor.js` (11 modules) | 42,549 B | 13,992 B |
| Same modules, map comment stripped | 10,603 B | 3,510 B |
| **Overhead** | **75%** | **4×** |

With external `.map` files the browser fetches them only when DevTools is open. Inlined,
every user downloads them on every cold load. Two consequences:

- **~10 KB gzipped of dead weight per visitor**, on a payload of ~100 KB — a tenth of the
  transfer, for something no user can use.
- **The TypeScript source is published to production.** `inlineSources` means the original
  `.ts` is readable in the browser. That may be fine for an internal tool; it should be a
  decision rather than a side effect.

The change appears incidental to the commit's purpose (adding tests). Reverting to
`"sourceMap": true` for Release builds, or setting `"sourceMap": false` and keeping inline
maps for Development only, recovers the 10 KB. **Worth fixing before these numbers are
compared against the other frameworks, all of which strip maps in a prod build by
default** — otherwise Blazor is penalised for a one-line config choice rather than a
framework property.

## 4. Cold load — Lighthouse 98

Mobile profile, Lighthouse's default simulated throttling: 1,638 kbps down, 150 ms RTT,
4× CPU slowdown. Repeated runs, best and worst shown.

| Page | Score | FCP | LCP | Speed Index | TBT | CLS | TTI | Transferred |
|---|---|---|---|---|---|---|---|---|
| `/` | 98–99 | 1.7 s | 1.8–2.0 s | 1.7–2.4 s | 0–70 ms | 0 | 1.8–2.0 s | 101 KiB |
| `/parts` | 97–99 | 1.7–1.8 s | 1.7–2.0 s | 1.7–2.4 s | 80–100 ms | 0 | 1.8 s | 108 KiB |

Cumulative Layout Shift is a clean **0** on both — server-side prerendering delivers the
markup in the initial HTML, so nothing reflows.

`/parts` carries 80–100 ms of Total Blocking Time against `/`'s 0–70 ms, which is the
interop modules parsing — and three quarters of those bytes are the source maps described
above.

### The caveat that matters most for this metric

**Lighthouse does not measure the thing that will actually determine how Blazor Server
feels in production.** Under `InteractiveServer`, first paint is server-rendered HTML —
which is exactly why these scores are excellent — but interactivity requires a SignalR
circuit to be negotiated and held, and every subsequent click, keystroke and sort is a
WebSocket round trip to the server. None of that is in FCP, LCP, TTI or the score.

Two specific distortions:

- **The server was on localhost**, so the round trip these numbers do not measure was
  approximately free. On a real network it is a real RTT per interaction.
- Doc 005 notes the SKU autocomplete fires **per keystroke** over the wire, for what is an
  in-memory lookup. A client-rendered SPA would do that with no network at all.

So: read "cold load 98" as *"first paint is genuinely excellent"* and not as *"the app is
fast"*. The two are the same statement for a React SPA and different statements for
Blazor Server. If the scoring sheet has one row for responsiveness, this metric will
flatter Blazor; the honest comparison needs a second measurement of interaction latency
under realistic RTT, which nobody has taken for any of the five frameworks.

## 5. Dependencies — 0 runtime deps added

The kit's starter is `dotnet new blazor`, which already ships Bootstrap in `wwwroot/lib`,
so Bootstrap is not counted as added.

| Category | Count | Packages |
|---|---|---|
| **NuGet, app project** | **0** | — |
| **npm, runtime** | **0** | — |
| npm `devDependencies` | 3 | `typescript`, `concurrently`, `json-server` |
| NuGet, test project | 6 | xunit, xunit.runner.visualstudio, Microsoft.NET.Test.Sdk, Moq, FluentAssertions, coverlet.collector |
| Deps for the TypeScript test suite | 0 | `node:test` / `node:assert` are built in |

**This is the strongest number in the set, and it is not a technicality.** The entire
screen — data grid with sort, filter and pagination, modal dialogs, async typeahead,
toasts, form validation — was built with zero third-party runtime code. `PartsBlazor.csproj`
contains no `<PackageReference>` at all.

Of the three dev dependencies, `json-server` is mandated by the kit and `concurrently` is
a convenience for running two watchers. **TypeScript is the only substantive addition**,
and doc 005 argues at length that adding it was the consequential architectural decision
in Track A. The dependency count is where that decision looks cheapest and the subjective
document is where it looks most expensive; both are true.

Also worth noting for the comparison: the TypeScript test suite added **zero** packages.
Node runs `.ts` directly via type stripping, so there is no test framework, no transform,
and no build step behind `npm test`.

## 6. Build/CI time — ~78–87s clean

After deleting all `bin`, `obj` and `node_modules`, with warm npm and NuGet caches:

| Step | Run 1 | Run 2 | Contended run |
|---|---|---|---|
| `npm ci` (126 packages) | 37.3 s | 42.4 s | 98.8 s |
| `dotnet restore` | 5.4 s | 8.1 s | 8.7 s |
| `dotnet build -c Release` | 44.1 s | 27.6 s | 56.7 s |
| **Total** | **86.8 s** | **78.0 s** | 164.1 s |

Additional steps, measured separately:

| Step | Time |
|---|---|
| `dotnet publish -c Release` | 20.1 s |
| `dotnet test` (1 xUnit test) | 9.2 s |
| `npm test` (1 `node:test` test) | 2.3 s |
| Warm incremental rebuild | ~8 s |

A single cold-cache observation (first-ever restore of these packages) came in at **67 s**
on the pre-`f03aec6` tree. CI without dependency caching should expect something in that
region or higher; CI with caching should expect the 78–87 s figures.

**npm is roughly half the clean build time.** `npm ci` alone is 37–42 s of the ~80 s
total, to install a toolchain whose entire output is 10.6 KB of JavaScript. That cost is
attributable to the TypeScript decision, not to Blazor — Track B, with no npm step at all,
is the control case and should be measured to confirm it.

One structural note for whoever wires up CI: `PartsBlazor.csproj` invokes `npm install` and
`npm run build` from a `BeforeTargets="Build"` MSBuild target, so **`dotnet build` shells
out to npm**. There is no way to build the C# without Node present on the agent, and the
two test suites need two separate commands (`dotnet test` and `npm test`) that no single
runner aggregates.

## Acceptance criteria

All 16 boxes in Kit §3 are ticked as of `f03aec6`. Three were failing when measurement
began and were fixed during it:

| Was | Now |
|---|---|
| Pagination 5/page | 10/page, per spec |
| No success feedback after create/update/delete | Toast with `role="status"` / `aria-live="polite"`, auto-dismissing |
| Error state unreachable on a cold API failure | `hasError` checked before the empty case |

The third was a genuine defect, not a missing feature: the template tested
`parts.Count == 0` before `hasError`, and `parts` starts empty, so an API outage on first
load rendered *"No parts found. Add one now."* — inviting the user to write to an API that
was down. Verified after the fix by stopping `json-server` and reloading: the error state
and its Retry button render, and Retry recovers once the API returns.

Save and delete failures now surface as an error-styled toast rather than setting
`hasError`, so a failed write no longer replaces the populated grid with an error panel.

Verified in the browser against the Release build: create, update and delete toasts all
fire; delete confirmation dialog appears; Save stays disabled until the form is valid;
**zero console errors** on a clean load; both test suites pass.

## What these numbers do not cover

1. **Track B is unmeasured.** It is the other half of doc 005 and it is on this machine at
   `C:\Github\Partscheck\blazor.demo.mia`. Metrics 2, 3, 5 and 6 will all move.
2. **Interaction latency under realistic RTT** — the metric that most determines how
   `InteractiveServer` feels, and the one Lighthouse structurally cannot see (§4).
3. **Concurrent-user capacity.** Circuit-bound scaling is discussed in 005; it is a load
   test, not a page audit, and no framework in the bake-off has been load tested.
4. **A cold-cache CI baseline**, measured consistently. One opportunistic observation
   (67 s) is recorded above; it was not taken on the current tree.
5. **Test coverage.** Metric counts are 2 tests, not coverage percentages. Doc 005 assesses
   what those tests are worth; the count alone flatters Track A.
