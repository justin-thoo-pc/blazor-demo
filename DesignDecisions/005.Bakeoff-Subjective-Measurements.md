# Blazor — Bake-off Subjective Measurements

**Status**: Draft for review.

Blazor was evaluated across **two independent implementations**. They made opposite
choices about where the C#/JavaScript boundary sits, and consequently explored
different halves of the problem space. Neither is a complete picture on its own,
and the disagreement between them is the most useful finding in this document.

| | **Track A** — `blazor.demo` | **Track B** — `blazor.demo.mia` |
|---|---|---|
| Target | .NET 10 | .NET 9 |
| UI | Hand-written components + custom CSS | MudBlazor 9.8.0 |
| Interactivity | `InteractiveServer`, **per component** | `InteractiveServer`, **global** (on `<Routes>`) |
| Authored TypeScript | 11 modules | **none** |
| `IJSRuntime` interop | 5 call sites across 3 components | **none** |
| Dependencies | NuGet + npm (`tsc`, test runner) | NuGet only |
| Components | 18 `.razor` | 12 `.razor` |
| Tests | 1 xUnit service test + 1 Node/TS suite | 10 xUnit tests incl. bUnit component tests |

**Track A** built more surface area — five static pages, a contact form, a reconnect
modal, per-browser activity tracking — and used TypeScript for everything browser-side.
It therefore hit the interop and toolchain problems hard, and never got to component
testing.

**Track B** built the parts manager only, leaned on MudBlazor for anything requiring
browser behaviour, and wrote no JavaScript at all. It therefore explored C# component
testing properly, and never encountered the TypeScript issues.

> **Fairness caveat, stated up front**: Track B avoided the interop problems partly
> because MudBlazor absorbed them, and partly because the features that *forced*
> interop in Track A (reconnect handling, activity tracking, custom dialog DOM) were
> not built. Read "Track B had no interop problems" as "Track B did not reach them",
> not as "they do not exist."

## Developer experience — hot reload, tooling, error messages

**Track A**

- Debugging C# and TypeScript are two separate exercises. C# breakpoints work normally
  under the debugger; the .NET debugger does not cover TypeScript, so front-end
  debugging is browser DevTools with its own workflow.
- **The two dev workflows are mutually exclusive.** Under a debug session, `.razor.css`
  changes do not live-update — the CSS-isolation bundle only regenerates at build time.
  Under `dotnet watch run` they do, but every full restart kills the debugger attachment
  and you reattach by hand. C# hot reload in the IDE is opt-in per change (the flame
  button) rather than on-save.
- TypeScript never hot-reloads. `tsc --watch` recompiles on save, but the browser needs
  a manual refresh. CSS is handled by `dotnet watch`, **not** by npm — two independent
  watch mechanisms to keep running.
- Stale-asset problem: `app.MapStaticAssets()` serves content-hashed, immutable-cache
  URLs, which can serve the old file after a recompile. Requires a hard refresh, and
  it is non-obvious when it is happening.

**Track B**

- One toolchain, so none of the above applies. `dotnet watch run` is the whole story.

**Combined**: the hot-reload complaints are **not inherent to Blazor** — they are the
cost of running a second build alongside it. A single-toolchain Blazor app has an
ordinary, unremarkable inner loop.

**Both tracks**: compiler and runtime error messages are clear and well-located. The
shared caveat is the browser console — under `InteractiveServer` all UI events are
WebSocket frames on `/_blazor`, so **they never appear in the Network tab**. You need
DevTools → WS → Messages, opened before page load. Losing per-interaction network
visibility is a real regression against a JS framework, and it applies to both tracks.

## Readability — would a teammate understand it cold?

**Both tracks**: the out-of-the-box directory structure is easy to follow, models are
well defined, and the backend is strongly typed end to end — the same `Part`/`PartDto`
type flows from service to component to markup with no serialization boundary. Track B's
`Features/Parts/` vertical slice reads slightly better than Track A's `Components/UI/`
split by kind.

**Track A — the typed boundary is not typed.** Both sides are strongly typed; the seam
between them is checked by neither compiler. Modules are resolved by compiled `.js` path
and methods invoked by string literal, with the return type supplied as an unchecked
generic assertion:

```csharp
var total = await _module.InvokeAsync<int>("recordItemAdded");
```

Two failure modes, both of which compile clean on **both** sides and break at runtime:
rename the TypeScript function (`tsc` doesn't know C# calls it; `csc` sees only a string),
or change its return shape (the `<int>` is a deserialization target, not a contract).
There is no go-to-definition, no rename safety, and no compile-time contract.

Blazor's typed alternative — `[JSImport]`/`[JSExport]`, which generates checked
marshalling — is **WebAssembly-only** and unavailable under `InteractiveServer`.

A symptom worth showing reviewers: `PartsGrid.razor.ts` exists in part just to
re-export `recordItemAdded` from `UserActivity.razor.ts`, so `PartsGrid.razor` can reach
it through a module reference it already holds. That file is a workaround for having no
shared typed access path.

**Track B**: no interop, so no seam. Typing holds end to end. The cost is fluency in
MudBlazor's component API and its conventions instead.

**Track A** additionally carries per-component `@rendermode InteractiveServer` as
cognitive load — a teammate must know which components are interactive and which are
static, and that is not visible from the hosting page. Track B's global render mode is
simpler to read but pays interactivity cost on every page (see *Other considerations*).

## Validation/forms story — how painful was the form?

**Track B — idiomatic and genuinely good.** `EditForm` + `<DataAnnotationsValidator />`
with `[Required]`, `[StringLength]`, `[Range]` declared on `PartDto`, and MudBlazor
inputs bound via `For="@(() => _editModel.Sku)"` expressions. Rules are declared once on
the model; the form, the error messages, and the touched/dirty behaviour all derive from
them. This is the strongest single result Blazor produced in the bake-off.

**Track A — hand-rolled, and worse for it.** Plain `<form>` with C# predicates
(`IsValidSku()`, `IsFormValid()`). `System.ComponentModel.DataAnnotations` is imported
but unused. It was quick to write and readable, but it demonstrates the cost of leaving
the framework: with no touched/dirty tracking, **every field displays its error the
moment the "Add Part" dialog opens.** `EditForm` provides that for free.

**Combined**: score this criterion on **Track B**. Track A's experience is evidence about
hand-rolled validation, not about Blazor's forms story, and would make the comparison
against other frameworks' idiomatic form stacks misleading.

## Testing story — how easy was the one test?

**Track B — 10 tests, one command, ~2 seconds, all passing.** One language, one
assertion library, one runner.

- *Model validation* — plain xUnit over `Validator.TryValidateObject`, with
  `[Theory]`/`[InlineData]` covering SKU length boundaries, missing category,
  non-positive price, negative stock. A real structural win: because validation is
  declared as attributes and the form derives from them, **the rules are unit-testable
  without rendering anything.** The test asserts the contract the UI is generated from.
- *Component tests* — bUnit renders the real dialog through the real `IDialogService`
  against a real DI container, drives fields with `data-testid` selectors and synthetic
  `.Change()` events, and asserts save-button enablement. Conceptually identical to React
  Testing Library; a teammate from a JS background would recognise it immediately.

Friction, all visible in the test file's own comments — and all attributable to
**MudBlazor, not Blazor**: `PopoverService` is `IAsyncDisposable`-only, so the class must
implement `IAsyncLifetime` or xUnit's synchronous teardown throws; and `PartFormDialog`
is `<MudDialog>` content that will not render standalone, so tests must host a
`MudDialogProvider` and open the dialog the way the page does.

**The significant caveat: `JSInterop.Mode = JSRuntimeMode.Loose`.** bUnit stubs every JS
interop call and silently returns defaults. It is required here (MudBlazor interops
internally), but it means component tests give **zero coverage of the C#/JS boundary**.
Set against Track A's finding that the same boundary is unverifiable at compile time,
this is the sharpest combined result in the document: **interop is neither type-checked
nor covered by the default component-test setup — it is only ever validated by running
the app.** Any app doing custom interop needs E2E tests, which is a third tool.

**Gaps in Track B**: both component tests assert button enablement; neither exercises
submit → API. `PartsApiClient` is registered against a live `HttpClient` pointing at
`localhost:4000` with no stubbed handler, so a save-path test would attempt a real
network call. The interesting integration is untested.

**Track A — two suites, two runners, two mental models**: xUnit + Moq + FluentAssertions
via `dotnet test` for C#, `node --test` for TypeScript. Every new test starts with "which
stack does this belong in?" The TypeScript side was the pleasant surprise — Node runs
`.ts` directly via type-stripping, so no build step and no framework to install. The C#
side is weak evidence: it tests a *service*, not a component, and it mocks `HttpClient`
directly (an anti-pattern — you mock `HttpMessageHandler`) on a method that never touches
it, so the mock is inert. bUnit was never added, so Track A never reached the actual
question.

**Combined**: Blazor's testing story is **good**, on the strength of Track B. Track A's
experience measures the cost of adding TypeScript, not the cost of testing Blazor.

## Docs & AI assist

**Both tracks**: official docs are thorough and Claude answered everything encountered —
no framework-specific sticking points.

One genuine hazard: .NET 8–10 substantially reshaped Blazor's hosting model, so much
published material (and LLM training data) conflates the old Blazor Server / Blazor WASM
split with the current Blazor Web App render modes. Answers need checking against the
version in use. Note the two tracks are on different targets (.NET 10 and .NET 9), which
is itself a small source of divergent guidance.

*(Tooling anecdote, not attributable to Blazor: Claude occasionally held a test port
open, requiring manual process termination.)*

## Other considerations

**Circuit-bound scaling — applies to both, but unequally.** With `InteractiveServer`,
each connected user holds a SignalR circuit with component state in server memory, so
capacity is bounded by **concurrent connections, not request rate**. That forces sticky
sessions and WebSocket support at the load balancer, and makes connection loss
user-visible.

The two tracks differ here and **Track A is better**: its per-component render mode means
genuinely static pages (Home, Reports, Settings) hold no circuit at all. Track B's global
`<Routes @rendermode="InteractiveServer" />` puts every page on a circuit whether it needs
one or not. If we proceed with Blazor, adopt Track A's per-component approach.

This is a property of the render mode, **not of Blazor** — `InteractiveWebAssembly` and
`Auto` have no circuit, at the price of a public CORS-configured API and a second project.

**Latency sensitivity**: every UI event crosses the wire, including each keystroke in
Track A's SKU autocomplete — which is an in-memory lookup that under WASM would not touch
the network at all. Fine on a LAN, poor on a bad connection.

**Compensating benefit**: because the API client runs server-side, the API URL is never
exposed to the browser and needs no CORS or public ingress. For internal apps behind a
corporate network that is a genuine security win, and it applies to both tracks.

**A tension worth naming**: `InteractiveServer` was chosen for API privacy and fast first
paint. It is the same choice that forces the circuit-scaling ceiling *and* rules out the
typed `[JSImport]` interop. Two of the three marks against Blazor here share one root
cause.

## "Would I maintain 50 of these?" — the gutcheck

**Qualified yes — and the qualification is the finding.**

The two tracks reached opposite conclusions, and the difference was entirely **whether
the app could stay inside C# plus a component library**:

- **Track B stayed inside it.** One language, one compiler, one package manager, one test
  runner, no untyped seam, and the strong-typing requirement met end to end. At 50 apps
  that is a genuine advantage over 50 TypeScript SPAs: no npm dependency surface, no
  bundler upgrade treadmill.
- **Track A stepped outside it** and immediately paid for .NET *plus* the full TypeScript
  toolchain, joined by a seam neither compiler checks and no component test exercises.

So the answer depends on a judgement call the framework does not make for you.
**Blazor leaves the C#/JS boundary decision entirely to the developer, with no guardrail
and a mild pull toward the wrong side** — interop-by-string is unpleasant enough that
once you are writing a JS module at all, you want types, and then a build, and then a
test runner. Track A shows how far that slide goes; at least one of its modules
(`UserActivity`) is almost entirely logic that belonged in C#, where it would also have
collapsed into the existing xUnit suite.

**Recommendation if we proceed with Blazor**: standardise on Track B's shape — a
component library for anything browser-side, `EditForm` + DataAnnotations for validation,
bUnit for component tests, no authored JavaScript — combined with Track A's
per-component render mode. Treat "we need to write a TypeScript module" as an
architectural decision requiring review, not a routine one, because it is the point at
which the framework's main advantage is lost.

**The open risk**: that discipline holds only while a component library covers our needs.
Track A's reconnect-state and `visibilitychange` listeners are exactly the kind of
requirement that breaks it — and under a strong-typing mandate there is no cheap escape,
since even a few lines of glue must then be TypeScript. Before committing, we should
check how many of the 50 apps have requirements of that shape.

**Not answered by either track, and probably decisive**: whether we have 50 apps' worth
of C# depth on the team.
